# إصدار «فرصة»

هذه قائمة تنفيذ لنقل المشروع إلى خدمة منشورة. تشغيل المعاينة أو نجاح البناء لا يعني وجود خدمة عامة أو قبولاً من App Store. لا توجد مفاتيح استضافة أو حسابات متجر مضمّنة.

## جهّز الخدمة والمشغّل

- [ ] اختر جهة التشغيل واسم المنتج النهائي وبريداً أو رقماً فعلياً للدعم؛ عيّن شخصاً يراجع الإعلانات والبلاغات ويستجيب للمستخدمين.
- [ ] انشر سياسة خصوصية وشروط نشر عربية على روابط HTTPS حقيقية، وضع روابطها ووسيلة الدعم داخل التطبيق وبيانات المتجر. وضّح أن رقم واتساب/بريد المعلن يصبح عاماً، وأن التواصل مع الجهة يحدث خارج التطبيق.
- [ ] أكّد مدة الاحتفاظ والحذف والنسخ الاحتياطية مع مشغّل الاستضافة؛ سياسة النص المنشور يجب أن تطابق التشغيل الفعلي.
- [ ] حدّد سياسة المراجعة: فرص حقيقية، وصف واضح، لا طلب دفع من المتقدم، إزالة الإساءة والخداع، حظر وسائل التواصل المسيئة، وطريقة اعتراض جهة حُظرت بالخطأ.
- [ ] جهّز محتوى إطلاق حقيقياً بموافقة جهات العمل. لا تنقل الأمثلة الخيالية إلى الخادم أو تعلن أرقام نجاح لم تُقَس.

## شغّل الخادم

اتبع [دليل الخادم](backend.md#نشر-فعلي-بـ-docker-وhttps) لإعداد نطاق وTLS وSQLite دائم وسر إدارة فريد وCORS محدد. أوامر Compose موجودة أيضاً هناك:

```bash
cd server
cp .env.example .env
# عدّل .env: ADMIN_TOKEN وAPI_DOMAIN وALLOWED_ORIGINS.
docker compose up -d --build
docker compose ps
```

- [ ] `/health` يعمل عبر HTTPS؛ منفذ API الداخلي غير مكشوف للعامة.
- [ ] السر محفوظ في بيئة الخادم ولا يظهر في تطبيق Flutter أو المستودع.
- [ ] اختبر نسخة احتياطية واستعادتها، وفعّل مراقبة الصحة ومساحة القرص والتعامل مع تعطل الخدمة.
- [ ] جدْول `docker compose exec -T api python maintenance.py` يومياً لتنفيذ مدة الاحتفاظ المعلنة.
- [ ] جرّب إرسال إعلان فعلي: منتظر ومخفي أولاً، ثم موافقة، ثم ظهور وتواصل، ثم بلاغ يصل للمشرف، ثم حذف صاحب الإعلان يزيله من الخادم.
- [ ] جرّب رفض إعلان وحظر ناشر مسيء والتأكد من عدم نشره مجدداً برقم واتساب أو البريد نفسه. الحظر ليس إثبات هوية؛ تابع المراجعة البشرية.

## اربط النسخة الحقيقية

- [ ] استخدم `API_BASE_URL` بعنوان الخدمة الفعلي عبر HTTPS، وفق [README](../README.md). غياب العنوان يشغّل المعاينة، ولا يصلح كإعداد متجر.
- [ ] تأكد أن الشارات التجريبية والفرص الخيالية لا تظهر في وضع الإنتاج، وأن القائمة الفارغة تشرح الحالة دون الادعاء بوجود فرص.
- [ ] تأكد من حفظ مفتاح الإعلان في التخزين الآمن، وعدم ظهوره في السجلات أو مشاركات التطبيق. فقدان الجهاز أو حذف التخزين قد يمنع الإدارة الذاتية؛ وفر مسار دعم واضحاً.
- [ ] جرّب حفظ وظيفة، إعادة تشغيل التطبيق، تغيير الفلاتر، إرسال إعلان، تحديث حالته، وحذفه. تحقّق من الأرقام العربية والأرقام السورية والبريد ومن حدود المدخلات.
- [ ] جرّب الاتصال الضعيف والانقطاع: تظهر رسالة واضحة، يبقى المحتوى المحفوظ مع تنبيه، ولا يدّعي التطبيق إرسال بلاغ أو إعلان لم يؤكده الخادم.
- [ ] قارن الفلاتر بفرص معروفة، بما فيها الرواتب ذات العملات والفترات المختلفة والفرص المنتهية. لا تعرض مقارنة مالية بين وحدات غير متشابهة.

## إصدار iPhone

- [ ] عيّن bundle ID مملوكاً للفريق وSigning Team من حساب Apple Developer، وبيانات الإصدار والاسم النهائي.
- [ ] ابنِ على Xcode/SDK مناسبين للمتجر وقت الرفع، ثم جرّب على iPhone فعلي؛ محاكاة iOS وحدها لا تثبت سلوك واتساب والبريد والتخزين الآمن.
- [ ] افحص الشريط الزجاجي والأيقونات الأصلية على نسخة iOS حديثة، والبديل المناسب على النسخ الأقدم التي يدعمها المشروع.
- [ ] افحص RTL، VoiceOver، حجم الخط الكبير، Reduce Motion، لوحة المفاتيح، المساحة الآمنة، والشاشات الصغيرة. الحركة لا تعيق إكمال المهمة.
- [ ] جهّز أيقونة ولقطات وبيانات متجر تعكس التطبيق الفعلي، وعمره المناسب، ورابط الدعم والخصوصية، وApp Privacy وفق البيانات والخدمات المشغلة بالفعل.
- [ ] أضف ملاحظات المراجعة: لا تسجيل دخول للمستخدمين، كل إعلان ينتظر المشرف، التواصل يفتح واتساب/البريد، كيفية الإبلاغ والحجب وحذف الإعلان. أبقِ الخادم متاحاً لفريق المراجعة.
- [ ] نفّذ تجربة TestFlight مع مستخدمين محدودين قبل توسيع الإطلاق، وتأكد من المراجعة البشرية للفرص خلال التجربة.

متطلبات المحتوى الذي ينشئه المستخدمون والخصوصية مدعومة بمراجع Apple الرسمية داخل [دليل الخادم](backend.md#متطلبات-إصدار-iphone-المتبقية-خارج-الكود). راجع السياسة الحالية وقت التقديم؛ هذه القائمة ليست ضمان قبول.

## حدود التحقق الحالي

تم توفير فحص API محلي تنفيذي بقاعدة مؤقتة يغطي دورة النشر والصلاحيات والبلاغات والحذف والصلاحية وCORS وحدود الطلبات. تشغيل Docker/HTTPS العام، اختبار التحميل، التوقيع وTestFlight وخدمة الدعم الفعلية تتطلب بيئة وقرارات المشغّل، ولا تُعد منجزة بوجود ملفات الإعداد. نتائج بناء Flutter الفعلية تسجل في تسليم المشروع، ولا تفترض هذه الوثيقة نجاح أي منصة لم تُبنَ.
